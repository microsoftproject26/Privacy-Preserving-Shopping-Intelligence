## 1. WB3 (fl/sparse_rows.py): OK

- **Encode / decode exactness.** A sent row carries the client's new FP32 value (sparse_rows.py:156-163). `decode` clones θ_r and `index_copy_`s the sent rows (:182-185), so a sent row is exact and an unsent row equals θ_r, i.e. zero delta (§5.3: "rows not sent = zero delta"). Tested at test_p2_sparse.py:68-89.
- **The server never reads unsent rows.** `decode(payload, theta)` takes no upload argument (:171). The channel builds the payload first, then decodes against the snapshot `self._theta` (:321-325). A poisoned upload is never seen, through decode (:129-141) or through the channel (:144-163).
  - The only reader of unsent rows is `_audit` (:288-307). It is a simulation-side oracle that a real server would not have (m6).
- **θ_r.** The snapshot is a clone of the item tensors only, taken at the round's first download (:278-286). The server state cannot change inside `run_round` (archived server.py:354-380), and retries do not re-snapshot.
  - The order is the same as Q8: upload() → acc.add() on the same dict, in-process only. `check_round` enforces it (:348-353), and the pool is refused (:344-346, :368-369).
- **Bytes.** The formula is dense FP32 + per group (4 + 4n + 4n·w) + the 8-byte header (:189-227). I recomputed it at production scale: 1,060,648 + 836,884 + 2,604 + 8 = **1,900,144 B** at 10 rows, which matches the handoff. The dense FA upload of 82,840,200 B is consistent with 20,710,048 shared numel.
  - §5.3 fixes no wire format, only "bytes come from the fl.comm ledger". The 4-byte row count (:59, handoff §7.2) is a reasonable framing choice. Accepted.
  - The ledger records the exact count, cross-checked against the formula on every visit (:326-333).
- **Joint output row set** (handoff §7.1). One class set for [W_j | b_j], ranked by the joint norm (:113-128). This is the natural reading of "top-k rows" with k counted in classes (2 % of K), and it keeps logit pairs intact. Accepted. It should be written into P2_METHODS_LOCK with the codec name.
- **k ≥ K equals dense.** `top_k_rows` returns arange (:121-122). Bitwise equality with the dense run is tested at round level (:217-221) and FLRun level (:260-275). This is lossless only because SGD_M has weight decay 0 (fl/client.py make_optimizer). The AdamW audit test shows the alternative (:224-227).
- **Tie-break.** A stable descending argsort sends ties to the lower id (:127). The code is right, but the test does not discriminate on CPU (m2).
- **Recentering.** I checked the handoff's claim of no gauge drift (§7.5): the softmax gradient has zero row-mean, and the server's `recenter_output_` shifts every logit by a constant. Truncation therefore adds no score change. Agreed (INFERENCE, consistent with sasrec_v2.py:405-411).
- **DP.** WB3 does **not** compose with DP: `install_sparse` refuses `cfg.dp` (:370), so the combination fails closed. In scope it is not needed, since §5.3 is FA. See open item O1 for WD.

## 2. WC LoRA (fl/peft.py): OK

- **B = 0 gives θ_pre exactly.** B is created as zeros (peft.py:89). `merged_weight` uses `where(d == 0, W, W + d)`, so no signed-zero flip is possible (:105-109).
  - Scores equal θ_pre's under `torch.equal`, and the merged digest equals `init_sha256` (test_p2_peft.py:86-97).
  - `state_digest` sorts keys (fl/numerics.py:98), so the shared-then-buffer order of broadcast_state does not matter.
- **Merged forward equals wrapped forward** within 1e-6, for r 4 and 16 (:113-125). With α ≠ r my probe measured 0.0. The merged key list and order equal the base SASREC_D64_B2 broadcast state (:121, peft.py:224-240), so reeval and export see the ordinary graph.
- **Only LoRA keys move through FL.** `freeze_all_but` rebuilds the manifest from `requires_grad` (peft.py:191-202), so only LoRA keys are trainable, uploaded, aggregated or clipped:
  - `extract_shared`, the optimizer groups, `clip_grad_norm_(adapter.shared_parameters())` (archived client.py:203, 223), fl.aggregate and fl.dp all iterate `manifest.shared_keys`;
  - every other parameter becomes a FIXED buffer, checked bitwise at each visit by `BaseAdapter.load_state_` (adapter.py:238-241);
  - recentering is switched off (peft.py:204-209);
  - combining with `freeze_item_tables` is refused (:176-177).
  - Tests: test_p2_peft.py:129-148 and :172-182. The negative control at :264-273 confirms that a worker with a different base is refused.
- **Resume.** latest.pt carries the LoRA broadcast state, so `FLRun.load_state_dict` restores A and B through the unchanged runtime. The manifest and init digests bind the structure (archived runtime.py load_state_dict). Tested bitwise, and the resumed run finishes on the straight run's digest (:229-242).
  - The endpoint payload holds the merged θ plus p2_lora, and `load_lora_from_payload` round-trips A and B (:243-259).
  - `install_peft` is idempotent and overrides `run.weights_payload` per instance. `self.weights_payload()` in `step` / `_evaluate` resolves to the override, so best.pt and endpoint_6.0.pt are both covered.
- **Init.** A uses `kaiming_uniform_(a=√5)` from one CPU generator seeded `derive_seed(seed, "p2_lora")`, consumed block by block, then target by target in order (:149-152). This is deterministic and device-independent by construction. The bound 1/√in is tested (:100-109).
  - The `generator=` keyword of nn.init is already used by v4models' own init (sasrec_v2.py:237, 243), so the server's torch supports it.
- **TO-CHECK: confirmed.**
  - `CausalBlock.forward_tokens`, `forward_padded`, `_attend` and `_ffn` call the modules (sasrec_v2.py:132-158).
  - The only direct `.weight` reader is `_xavier_linear`, which runs at construction (:233-238).
  - A repo grep found no other reader of qkv / out / ff1 / ff2 weights.
  - The `weight` property returning W_eff (peft.py:94-96) is a sound extra guard.
- **Bytes.** 4 · 2,048 · r per visit, plus the 8-byte header on the upload. The frozen base is counted once through `visit_bytes(frozen_keys=…)` (:185-201).

## 3. Wiring instructions (handoff §5): mostly complete, two gaps

- **M1 (must fix before the WB3 hook).** Archived launch_fl.execute calls `install_q8` whenever `spec["upload_codec"] is not None` (launch_fl.py:1542-1544). `bytes_record` likewise switches to `q8_visit_bytes` on any non-None codec (:1179-1185).
  - The handoff tells P2-02 to put `{"name": "SPARSE_ROWS_WB3", "k_top": 3170}` in `upload_codec`, and P2-02's draft hook docstring already reads `spec["upload_codec"]["k_top"]`.
  - Unless both branches dispatch on `codec["name"]`, or k_top moves under `p2_recipe`, the result is one of two failures:
    - the round loop fails closed (`run.channel is not q8`);
    - worse, the summary carries a silently wrong Q8 `per_visit` / `per_client` bytes block. Bytes per visit are selection tie-break (1) in §5.6.
  - §5 must say this explicitly.
- **M2.** `SparseChannel.totals` and `round_stats` live only in the process (sparse_rows.py:273-276, 355-360). After any resume, `sp.summary()` covers only the last leg, yet the handoff puts it under `bytes["sparse_codec"]`.
  - The WB3 per-visit upload figure, which is also the §5.6 tie-break scalar for a client-dependent upload, should come from checkpointed state: `ledger.bytes_up / Σ counters.visit_counts`.
  - `sp.summary()` should be labelled "this leg, monitoring".
  - The definition of "upload bytes per visit" for WB3 should be fixed in P2_METHODS_LOCK (P2-06 / Ops).
- **m3.** The WB3 spec bullet in §5 omits the item-LR multiplier × 0.1 that §5.3 requires for WB3. That multiplier belongs to P2-02, but the bullet should name it.

The LoRA steps are complete and minimal: apply_lora, freeze_all_but, lora_init_sha256, the worker bootstrap, then `Server`, then `install_peft` after construction and after resume, and `frozen_keys_of` for `bytes_record`.

- **m2.** The stable-tie test (test_p2_sparse.py:92-101) passes with `stable=False` on CPU, so it does not discriminate. Use a larger tie block, e.g. 50 tied rows with k cutting inside it, or assert against a reference built with an explicit lexicographic sort.
- **m5.** Lossless item rows and touched-row coverage are tested on TinyRec only. Add a SASRecCE case like my probe (K ≈ 3,000, a few seconds on CPU), asserting moved ⊆ touched and `item_dropped_max_abs == 0`.

  - The regression risk is very small, since no existing file was edited and nothing imports the new modules. The claim must still not be stated without numbers.

## 6. Disclosures and open items (INFERENCE unless marked)

- **m6 (disclosure for any WB3 claim).**
  - The WB3 upload sends the client's touched item ids **in the clear**, i.e. its history and target items, and the top-k output ids correlate with its targets. This is the known item-set leakage of sparse federated-recommendation updates.
  - Per-client index sets are also incompatible with standard SecAgg, which needs a common dense index set.
  - This bears on E3 / E4 (§7.3 / §7.4) and on the Edge narrative. It should be registered beside the WB3 bytes.
  - The audit fields are a simulator oracle and should be labelled that way.
- **O1.** §5.5 carries over only W*'s server optimiser, server LR and client LR into WD.
  - If W* = WB3, `install_sparse` refuses DP. Ops / Fable must rule whether WD then runs dense with the same item-LR, or whether WB3 + DP is built.
  - If W* = WC, DP over the LoRA keys works in fl.dp. However, launch_fl's `dp_noise_dimension.frozen_keys_excluded` reads `spec["frozen_item_tables"]` (launch_fl.py:1581-1585) and would list nothing.
- **O2.** For P2-01 / Ops: with LoRA, D1-ext's T is the set of A / B keys. Since A starts random, `rel_pre_dist` and §3.2(a) "relative distance on T < 1 %" do not measure how far the merged model moved from θ_pre. For WC, T should be defined on the merged wrapped weights against θ_pre.
- **Nits:**
  - The code and handoff cite "PREG2 draft §5.3 / §5.4". They should cite PREG2.md be0561ab. I diffed the two: §5.3 / §5.4 differ only in wording.
  - peft.py:21-22 says "fl.aggregate verifies a worker's copy". In fact `BaseAdapter.load_state_` does.
  - p2_lora could also store `theta_pre_digest` and the LoRA init hash, for lineage in P2-08 reeval.
  - "Non-item numel 265,162 vs 263,822" should be TO-VERIFY against the server manifest before any bytes claim.
