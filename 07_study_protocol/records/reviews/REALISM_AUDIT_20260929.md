## 0. Verdict (OPINION, evidence below)

**No HARM to data, privacy of real people, or to the sealed TEST was found. Nothing already run is wasted.** The programme is a
clean, pre-registered *algorithmic* comparison. But measured against the owner's standard — "as if I actually had this system in
Edge" — the **federated arm as registered is not what a production FL system would do, and the just-read CALIB screen shows it is
badly under-optimised**: FA on CALIB reaches ≈ 0.026 against ≈ 0.11–0.12 for the central model on the same users (≈ 20–23 %
retention, INFERENCE), the local LR was selected at the TOP of a 3-point grid while still rising (+16 % and +9 % per doubling),
and the design combines four choices no production system uses together: (i) plain FedAvg with server LR 1 and **no server
optimizer**, (ii) **client AdamW re-created every visit with ≈ 4 steps** (sign-like updates), (iii) the central warmup–decay LR
shape mapped onto rounds so **≈ 2/3 of the rounds run at ≤ 0.1 × peak**, (iv) an **equal-example-exposure budget** (6.0 EFE, ≈ 3
visits per client, 6,827 averaged updates) instead of the rounds a deployment would run. Reported as "FL retains ~20 % of cloud
quality" this would be **unfair to FL and misleading about Edge**; reported as "FedAvg-with-client-Adam at a 6-EFE budget retains
~20 %" it is a legitimate lower bound. The thesis must say which — and the cheap fixes below move it toward the former.

Two further realism corrections must enter the thesis text before any value is read (they change *claims*, not runs): (a) in every
non-DP federated arm the uploaded delta **reveals the user's viewed items to the server** (the input item table's non-zero rows are
exactly the items in the visit; no secure aggregation) — "only weights leave the device, for privacy" is data minimisation, not
privacy; (b) the DP arms' utility is dominated by the simulated population and model size (N = 131,072, d = 20.7 M, m = 1,024 →
per-round noise 2.5 S vs McMahan 2018's 0.23 S at C̃ = 5,000 / d = 1.35 M) — an Edge-scale deployment (10⁷ users, report goal ≈
6,500) sits ~10× lower in noise-to-signal, so the DP result is a property of this simulation's scale (already half-registered in
06D §3; must be completed with the population argument).

**MUST before any downstream value is read (all cheap; details §G):** (1) extend the FL LR screen upward (×4, ×8, doubling until the
optimum is interior; amendment 06F; two CALIB runs ≈ 2.7 h each in parallel) and **HOLD the S_CAL → FA_1024 → DP lane** until it
ends (S and every DP run depend on the local LR); (2) register the realism disclosures of §B/§C as thesis text (zero cost);
(3) register R(arm / C_FULL) for FA, FT_C, LO as confirmatory co-headline contrasts (analysis only; C_FULL is running).
**SHOULD-high:** a production-realistic FL arm with server momentum (FedAvgM, β = 0.9; ≈ 100 lines in `fl/server.py` + tests +
review; screened on CALIB like FA), FA_X2 promoted from NICE, and one DP point at realistic scale (m ≈ 8,192–10,240 on the
1.35 M-user TIEBREAK band, evaluated on the same MAIN_VALIDATION rows) instead of DP ε = 1 at MAIN scale.
